# nxr-io in WebAssembly: a data client the Cortical Flow Studio can use (2026-11-11)

## Goal

"We have now added a pretty robust set of IO modules that can read, write, update and work with nxr zarr files … it makes it possible for apps
like the Studio to work with Zarr via nxr-neuro … we need to start building the WASM for the file operations as a priority." And: "we are
developing the WASM and making nxr-neuro accessible by the Studio. Focus on that and keep building it."

## The seam: the Studio's `DataClient`

The Studio's app reaches storage through one interface, `DataClient` (`nxr-cortical-flow/backend/src/client.ts`). Two implementations exist:

- `dataClient(base)`: the desktop data service over HTTP (Node, the Studio's TypeScript `@nxr/io`), reading and writing.
- `servedClient(root)`: a published root over HTTP (zarrita and SQLite-wasm), read-only.

nxr-neuro adds a third: **`wasmClient(datastore)`**, the same interface, in process, backed by nxr-neuro's `io/` compiled to WebAssembly. The
Studio can then use nxr-neuro wherever it uses a `DataClient`, without a change to the app.

## What it is, in layers

1. **`io/` in WebAssembly** (done, PR #41): the core of `io/` builds under Emscripten (SQLite 3.51 amalgamation, zlib, c-blosc's zstd, WebAssembly
   exceptions); no Brainstorm importers.
2. **The bundle in `io/`** (`nxr/io/bundle.h`): `subject_bundle(db, subject_id)` and `bundle_by_path`, a port of the Studio's `bundleOf`
   (`backend/src/db/bundle.ts`): every row a subject's model needs, following the default subject's rows its own rows name. The reference is the
   Studio's; the test compares the two on the same database.
3. **The module** (`bindings/wasm-io/src/binding.cpp`, Embind): a `Datastore` opened on a datastore folder, with JSON in and out for rows and typed
   arrays for array data:
   - `status()` (the catalog), `bundle(storePath)`, `view(name, whereJson, limit)`, `row(table, id)`;
   - `read(storePath, arrayPath, sliceJson)` → bytes and dtype; `create(storePath, arrayPath, metaJson)`, `put(storePath, arrayPath, data, region)`,
     `remove(storePath, arrayPath)`.
   - Errors are thrown to JavaScript as `Error` with the `io` error code (`err.code`).
4. **The client** (`bindings/wasm-io/js/index.mjs`, `index.d.ts`): `wasmClient(datastore)` returns the `DataClient` shape (promises, typed arrays).

## Where it runs: who supplies the files

The WASM sees only the files its host gives it.

- **Node (first):** the real disk (`NODERAWFS`). This serves the Studio's desktop app, whose data service runs on Node.
- **Browser, a folder the user grants** (File System Access API, Chrome/Edge): in a worker, through Emscripten's WASMFS. Next.
- **Browser over HTTP** (published roots): needs `io/` to read through a byte-range layer instead of files. Last; zarrita covers it today.

## Order

1. **Read side and array writes** (done 2026-11-11; `test/parity.sh`, 136 checks against the Studio's code):
   - status, bundle, views, rows and array read;
   - array create/put/delete. `put` writes any region (`io/`'s `write_region`, read-modify-write of the chunks it touches, since 2026-11-11;
     the Studio writes regions along any axis, e.g. `save.ts`'s `[[0, K], [f0, f1], [0, 4]]`).
2. **Row writes:** `selections`, `fields`, `operators`, `manifolds`, `dictionaries`, `measurements`, `subjects.put/delete`, `layout`, mapped onto
   `SubjectWriter` (row pending → bytes → row complete, D59).
   - **Done:** `subjects.put`, `subjects.delete`, and `fields.post` (saving a result: virtual or stored, the array's layout read off the store, the
     value count checked against the manifold's cells (`nxr/io/cells.h`, the Studio's `cells.ts`), contributions and child selections, then the sync
     drain). A field made by an operator FROM an input must meet its step (the Studio's `stepProblems`, ported).
   - **Done:** `selections.post/put/delete` (children: extents, spans, its own measurements) and `measurements.post/get/delete` (`nxr/io/measures.h`: the
     registry, generated from the Studio's into `io/schema/measures.json` by `tools/gen_measures.mts`; the roll-up query; derived measures from their
     rolled-up ingredients; the `measure` dictionary).
   - **Done:** `operators.post/put/delete` (analytic or stored, checked against the stored array(s); the cells, the inverse pairing and the
     composition's chain; factors) and `fields.put/delete`; the operator step check is tested end to end.
   - **Deletes take their arrays (D164)**, as the service's routed deletes do (`deleting_rows` in `io/`): the paths the subject's rows named before and
     none names after are removed through the store-node checks. `arrays.delete` is refused while a row names the array. The test compares every
     file of the two datastores.
   - **Done:** `manifolds.post/put/delete`: a product built from its factors (the Studio's `productManifoldFrom`), or a row with its topology (+ cells)
     and geometry (+ dimensions), a `coordinate_system_key` resolved to the subject's system (`coordinate_system` in `io/`). A delete takes the
     geometry and the arrays.
   - **Done:** `dictionaries.post/put/delete` (an app-scope one written to every dataset; an update touches the selections reading it; a delete
     refused while one does) and `jobs.get/post/put` (the stamps as a job runs and finishes), routed to their dataset as the service routes them.
   - **Done:** `layout`, where a node goes: with a manifold of the subject, or one about to be written (a type with its role, operator or name; a
     product's factors, ids or `<type>:<role>`). It uses `io/`'s `folder_of` / `folder_for`, with the Studio's refusals (JSON-quoted names, where
     `io/` words them as nxr's Python does).
   - **Done: dataset operations** (outside the Studio's DataClient: its main process's model service does them). `datasets.create(name, source)`
     is the Studio's `ensureDataset`: idempotent by name; the database, rows, folder, band dictionary and catalog entry. `datasets.delete(name)` is its
     `removeDataset` (D167): the whole folder and its catalog entry; one not there is not an error. `datasets.catalog()` rewrites the catalog. A
     dataset made is stamped `built_by` the client's `program` (default `nxr-neuro`; the Studio's service says `cortical-flow`), separate from the row's
     creator (`CreateOptions.built_by` in `io/`).
   - **Done: imports, through the command line itself**.
     - **What is compiled in:** the whole of `io/`, the Brainstorm importers with matio (zlib, no HDF5), and the command line's own code
       (`cli/nxr_neuro.cpp`, `convert_command.cpp`, `read_command.cpp`, its `main` renamed).
     - **`imports.post`:** the Studio's `importSubjects` + `importBrainstorm`. It runs `nxr-neuro convert convert|template|group` (and `subject
       delete` for a replace) in-process, with the arguments the Studio gives its converter.
     - **`cli(argv)`:** the command line itself, for anything else.
     - **A v7.3 `.mat` (HDF5):** refused by name in WebAssembly ("re-save it as v7, or convert it with the native nxr-neuro").
     - **A `store` source** (copying a subject store in) is not ported.
     - **Test:** `test/parity_imports.mts`. The Studio's own service runs the native `nxr-neuro` as its converter, wasmClient runs the same
       command in the module. Every table, file and `zarr.json` are equal, deterministic on both sides, for a subject and its condition, a replace
       and a template with its MRI.
     - **Module size:** 4.9 MB.
   - **Done: the analysis commands**.
     - **What is compiled in:** `compute/`, `meeg/` and `pipelines/`. The in-process command line runs every analysis verb: `eigen solve`,
       `headmodel`, `noisecov`, `inverse`, `psd`, `sourcepsd`, `quadrature`, `hodgepower`, `opticalflow`, `speedspectrum`, `frames`, `tiles`, the
       filters.
     - **Module size:** 7.6 MB, 2.5 MB gzipped, 1.7 MB brotli.
     - **Exceptions:** one model for every object (`-fwasm-exceptions`).
     - **Test** (`test/parity_analysis.mjs`, synthetic session subject):
       - Each command runs natively and in the module, deterministic on both sides; exit codes, result lines, every table and every file
         compared: `noisecov`, `psd`, `lowpass`, `headmodel`, `inverse`, `sourcepsd`, `tiles`, `frames`, `eigen solve`.
       - Arrays are bit-equal, or equal to the last places: the native arm64 build fuses multiply-adds and sums in NEON lanes, WebAssembly
         does neither. Measured: noise covariance and whitener ≤ 3.5e-15 relative.
       - The eigensolve is held to its iterative tolerance: eigenvalues 3.8e-11, float32 eigenvectors 5.8e-8.
       - Its fixture is a bumpy sphere, because a symmetric mesh has repeated eigenvalues whose eigenvectors may turn.
     - **Not yet in that test:** `quadrature`, `hodgepower`, `opticalflow`, `speedspectrum`. They need a mode package or wavelet bank on the fixture.
   - **Done: the geometry compute on meshes in memory**, for the Studio's interactive use.
     - **What is compiled in:** the compute binding's Embind (`bindings/wasm/src/nxr_compute_wasm.cpp`: the Manifold context — operators, DEC, eigenmodes,
       frames, heat and exact geodesics, vector heat transport, the log map, signed heat, smooth fields, stripes, BFF, …).
       Its JS surface is `bindings/wasm/js/wrap.mjs`, now shared by the standalone build and this module.
     - **`nxrNeuro()`:** one instance with `compute` (that API) and `client(root)` (the data client, with every analysis verb through `cli`).
     - **Link options carried over:** an 8 MB stack (Eigen's sparse Cholesky), the heap views and malloc/free the wrapper uses, the exception
       message helper.
     - **Test:** the compute binding's smoke (`bindings/scripts/_smoke-wasm.mjs <module>`): every raw and wrapped check passes on this module.
       Separately: one instance read a surface from a datastore and solved its eigenmodes in memory.
     - **Module size:** 8.5 MB.
   - **Where nxr-neuro deliberately differs from the Studio** (each written down, and asserted by the test where it shows):
     - **A deleted manifold's topology and geometry.** A manifold points at its topology and geometry, so the database's cascade does not take them
       with it. Since 2026-11-11, nxr-neuro and nxr (`delete_row`) delete, with a manifold and its cascading components, every geometry
       and topology of the subject no manifold stands on any more. A shared one stays (the pial's sphere shares the pial's topology). The Studio's
       current service still keeps the topology row and its faces. That no longer matters once the Studio goes through nxr-neuro, and the test asserts
       it as the one known difference.
     - **An absent column is NULL.** The Studio's service cannot bind an absent manifold or geometry column (node:sqlite refuses `undefined`), so its
       callers give every column. nxr-neuro writes NULL. The two agree whenever the Studio's own callers are used.
   - **Strings:** Embind's `std::string` is UTF-8 (`EMBIND_STD_STRING_IS_UTF8`).
   - **The writer lock in WebAssembly** names the real process: under Node, `process.pid`, `os.hostname()` and `process.kill(pid, 0)` replace
     Emscripten's fixed stand-ins (pid 42, host `emscripten`). Before, no other writer could tell a live holder from a dead one. `test/parity_writes.mts` runs the same calls through the Studio's own service
     (`createModelService`) and `wasmClient` on two copies, and compares every table and the catalog.
   - **Held datasets:** a dataset written is held open with its writer lock until `close()`, as the service holds the datasets it serves. A reopen
     runs the recovery, which settles pending sync jobs early, and the queue then differs from the service's.
3. **The browser folder connection** (next).
4. **HTTP reads.**

## Validation

- **Synthetic data only.** Each step has a test that does the same thing through the Studio's own code and through `wasmClient`, and compares:
  - the bundle against `bundleOf`;
  - the arrays against the Studio's `read`;
  - the rows written against the data service's.
- **The round trip with the native CLI** stays (`bindings/wasm-io/smoke.sh`).
